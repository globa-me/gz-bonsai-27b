# Локальный RAG по документам

## Что реализовано

Начиная с релиза `0.5.0` приложение поддерживает локальную базу знаний для каждого чата:

- форматы PDF с текстовым слоем, DOCX, TXT, Markdown, CSV и JSON;
- извлечение и индексирование выполняются Rust-бэкендом без облачных API;
- документы разбиваются на перекрывающиеся фрагменты примерно по 1400 Unicode-символов;
- для небольших документов сначала собирается полный текст без повторения overlap и проверяется число токенов через локальный `llama-server` `/tokenize`; если документ не помещается в отведённую долю контекста, BM25 выбирает до пяти релевантных фрагментов;
- найденные фрагменты считаются недоверенными данными: prompt запрещает выполнять инструкции из документов;
- ответ сохраняет снимки локальных цитат `[D1]`, `[D2]` по документам, поэтому названия и выдержки остаются видимыми в истории;
- один и тот же документ определяется по SHA-256 и не индексируется повторно;
- индекс хранится в `Application Support/com.bonsai.desktop/rag/documents`, исходный абсолютный путь не сохраняется.

Документы подключаются к конкретному чату. Отключение документа убирает его из последующих поисков, но не переписывает старые ответы и их цитаты.

«Недоверенные данные» здесь — техническая граница prompt injection, а не оценка истинности документа: модель может извлекать факты, но не должна исполнять команды, случайно или намеренно записанные внутри файла. Начиная с `0.5.1`, эта служебная формулировка не должна повторяться в пользовательском ответе.

Начиная с `0.6.0` файл физически не разрезается. Индекс хранит перекрывающиеся текстовые части примерно по 1400 символов с overlap 220 символов, чтобы важная фраза не потерялась на границе. Новые индексы дополнительно сохраняют нормализованный полный текст; старые индексы версии 1 читаются с удалением перекрытий по совпадающим границам (для них точное восстановление всех пробелов не гарантируется). Когда суммарный текст выбранных документов умещается в предел 9000 символов и занимает не более 60% контекста по результату `/tokenize`, он передаётся модели целиком. Иначе применяется BM25. Интерфейс показывает один файл как один документ и объединяет цитаты из его частей. Ошибка RAG блокирует отправку запроса, чтобы модель не отвечала без обещанных документов.

Ограничение 9000 **символов** не зависит от размера контекста в **токенах**: прежнее сравнение этих разных величин ошибочно отклоняло некоторые PDF. Если длинный файл не помещается, запрос о его начале и конце получает короткие выдержки именно с двух краёв; запрос о файле целиком получает распределённые выдержки с начала, середины и конца. Это не означает, что модель прочитала весь длинный файл. Для остальных вопросов действует BM25.

Инструкция модели перечисляет только метки реально переданных документов. Это устранило наблюдавшуюся в нативном тесте ложную ссылку `[D2]` при единственном `[D1]`; генеративные цитаты всё равно требуют проверки по показанным источникам.

Документы можно также перетащить в окно чата. Начиная с `0.6.0` PDF и DOCX автоматически подключаются к документам чата; для TXT, Markdown, CSV и JSON интерфейс предлагает выбрать «к сообщению» или «к документам чата»; изображения и код добавляются к запросу.

## Ограничения безопасности и ресурсов

- исходный файл: максимум 20 МБ;
- извлечённый текст: максимум 4 млн символов;
- до 12 документов на чат;
- в один запрос попадает до 9 тысяч символов документального контекста; небольшой документ может попасть целиком, длинный — только выбранными выдержками;
- scanned PDF без текстового слоя не поддерживается: OCR пока не входит в приложение;
- зашифрованные или повреждённые PDF/DOCX возвращают явную ошибку;
- содержимое RAG-документов не отправляется провайдеру веб-поиска и не входит в диагностический отчёт.
- «Убрать из чата» снимает привязку; «Удалить с устройства» удаляет JSON-индекс, только если тот не используется другим чатом. Уже сохранённые ответы и цитаты остаются в истории.

Точный подсчёт токенов относится к тексту документального контекста и недавних сообщений, но не к полному шаблону чата `llama-server`. При длинной истории, вложениях или мультимодальном запросе сервер всё ещё может вернуть ошибку переполнения контекста. Следующий шаг — проверять собранные `messages` через API подсчёта токенов шаблона чата на закреплённой версии runtime.

## Почему пока BM25, а не embeddings Bonsai

Встроенный PrismML runtime предоставляет `/v1/embeddings`, но только если запустить отдельный процесс с `--embedding`. Обычный chat-server возвращает HTTP 501, а документация рекомендует использовать режим с отдельной embedding-моделью. Фактическая проверка causal embeddings Bonsai 1.7B показала слабое разделение связанных и несвязанных русских фраз, поэтому они не используются как продуктовый semantic index.

Текущий этап — честный sparse-RAG: он особенно хорошо находит имена, числа и точные термины, не требует второй модели и не увеличивает память во время чата. Следующий этап — hybrid retrieval: отдельная проверенная multilingual embedding-модель + lexical BM25, объединённые через rank fusion. До включения в релиз нужно закрепить commit URL, размер, SHA-256 и лицензию embedding GGUF, а также измерить дополнительную unified memory на нескольких M-series.

Первичные источники:

- закреплённая документация PrismML llama-server по embeddings: <https://github.com/PrismML-Eng/llama.cpp/blob/prism-b10709-9a9394a/tools/server/README.md#post-v1embeddings-openai-compatible-embeddings-api>;
- upstream llama.cpp о выделенном `--embedding` режиме: <https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md>;
- кандидат для будущей проверки, multilingual BGE-M3: <https://huggingface.co/BAAI/bge-m3>.
